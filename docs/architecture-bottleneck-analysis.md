# 博客架构性能瓶颈沉淀（next-typecho）

更新时间：2026-07-26

本备忘用于后续重构/优化时的基线对齐，不是一次性修复清单。

## 一、结论（先看这）

当前瓶颈不是单点，而是“动态请求链路过长 + SQLite 单机约束 + 重计算查询 + 渲染开销”叠加。

如果你要优先提 QPS，建议按三层推进：

1. 降低每请求服务端工作量（缓存+减少实时查询）
2. 处理数据层并发瓶颈（SQLite 访问模式）
3. 调优 Node/进程与反向代理

## 二、当前瓶颈清单（高→低）

1. 全站公开页强制动态渲染
- 当前公开路由（首页、分类、标签、文章详情等）多处写了 `force-dynamic`。
- 结果：高并发时每次请求都会命中服务端执行数据库 + 渲染。

2. 单库 SQLite + 高频查库
- 使用 `node:sqlite` 的单文件 SQLite，读写共享同一文件。
- 随请求数增大，会出现锁竞争、等待与波动。

3. 列表查询链路包含计数/聚合/附加查询
- 文章列表/侧边栏会执行 count、排序、分类聚合、标签补齐等。
- 这在列表页/文章页每次刷新都会反复计算。

4. Markdown 每次请求实时解析
- `react-markdown + remarkMath + rehypeSanitize + rehypeKatex + Mermaid` 在服务端逐次解析。
- 长内容文章会明显放大 CPU 时间。

5. 站点主布局每次解析登录态
- 主布局会读取 cookie 并查 session，导致公开路径也有数据库读。

6. 缺少显式缓存策略
- 未建立稳定的页面级/片段级缓存边界（除非业务层显式触发），公共内容容易高频重算。

## 三、数据库瓶颈细节

涉及文件：
- [src/lib/db.ts](/Users/faris/Code/Personal/next-typecho/src/lib/db.ts)
- [src/lib/repositories/posts.ts](/Users/faris/Code/Personal/next-typecho/src/lib/repositories/posts.ts)

主要风险：
1. 大量 `count(*)` 与列表分页每次命中
2. 管理后台与访客侧都共用同库对象
3. 文章详情页附加查询（相邻文章 + 目录/侧边栏）未做缓存

## 四、首版优化方向（建议你后面直接按这个顺序）

### 阶段一：最小侵入（先上手）

1. 把公开页从全强制动态改为可缓存
- 只对管理员相关路径保留动态。
- 公开内容用可控的 `revalidate`/缓存策略。

2. 侧边栏与归档类查询做服务端缓存
- `recentPosts`、`categories`、`archives` 建议 cache（内存/文件/Redis 任一）
- 对应变更动作触发 `revalidate`。

3. 首页/分类/标签列表增加查询缓存
- 查询结果按 `page+slug+size` 缓存 60~300s。
- 避免同一时间大量重复 SQL。

4. 文章页面 Markdown 输出做预生成缓存
- 发布时产出 HTML 缓存片段，详情页直接透传。

### 阶段二：并发增强

1. Node 启动参数与 worker 策略
- `NODE_OPTIONS` 与 `max-old-space-size` 根据内存情况分步上调。
- 结合 CPU 数评估 worker 数，不要一次性开太多。

2. SQLite 并发防抖
- 控制长事务时间。
- 查询尽量走索引友好 SQL（避免无索引字段筛选）。

3. 增加 Nginx 缓存（静态优先）
- 静态资源长期缓存。
- 首页与列表 API 可用短 TTL 缓存。

### 阶段三：中长期

1. 如果增长明显，再考虑数据库拆分到托管服务（PostgreSQL/MariaDB）。
2. 将“统计”与“内容渲染”异步化（生成式字段/后台刷新）。
3. 引入监控告警（QPS、P95/P99、DB wait、GC）形成回滚闭环。

## 五、风险提示

- 只调 Node 堆内存能提升稳定性，但 QPS 天花板通常仍被数据库和热点查询卡住。
- 不要用“盲目提高堆”替代缓存与查询降本。
- 所有优化必须结合压测或真实压测指标评估，不建议一次改太多。

## 七、架构演进建议（建议下周直接接着做）

### 7.1 先把“读路径”先变轻（最省事最快见效）

1. 公开页默认改为静态/半静态
   - 首页、分类页、标签页、文章详情页按“更新频率”建立不同缓存粒度。
   - 先不大改逻辑，只做最小入侵：给列表和详情的关键查询加 `revalidate`。
   - 对“搜索”“个人设置”“后台”保留动态。

2. 文章详情二层缓存
   - 详情页内容在发布时预生成 `HTML 片段`，详情页优先读缓存。
   - 若缓存失效，则回退数据库查询 + Markdown 实时渲染。
   - 发布、更新、删除文章后立即清理相关文章缓存。

3. 侧边栏和归档类查询做“共享层”
   - 最近文章、热门文章、分类列表、标签列表改为统一的服务层查询缓存。
   - 这些请求在首页和文章页都复用，避免重复扫描数据库。

### 7.2 再处理“数据库与索引”层

1. 统一检查并补充索引（重点）
   - `posts` 表上 `slug`, `createdAt`, `status`/`isDeleted` 等过滤字段。
   - `taxonomies` 和 `post_taxonomy_relations` 的连接列要有明确索引顺序。
   - 任何分页接口都必须有固定的 `ORDER BY + 限制字段索引`。

2. 避免“先查列表再逐条补数据”的 N+1 结构
   - 评论、标签、分类等附属数据优先一次性 join 拉取。
   - 如果一次性 join 成本过大，改为批量批次读取，减少每条请求次数。

3. 控制 SQLite 并发策略
   - 保持写路径短事务，避免长时间持锁。
   - 如果评论/点赞成为热点，先做异步队列/聚合更新，再落库。

### 7.3 最后做“服务端能力面”

1. Node 进程
   - 先稳态 `--max-old-space-size=1536` 或 `2048`，不要盲目上到太高。
   - 观察 GC、RSS、P95、P99 后再决定是否增加实例数。

2. Nginx 层
   - 为静态资产做长期缓存。
   - 对热门公开路径启用短 TTL（例如首页骨干 JSON / 部分列表片段）。
   - 继续保留 gzip / brotli 的静态压缩策略。

3. 监控闭环
   - 公开路径响应：QPS、P50/P95/P99、错误率。
   - 数据库等待：连接等待、锁等待、慢查询计数。
   - Node 健康：进程内存、CPU、GC 次数/耗时、事件循环延迟。

## 八、快速排障清单（你后面改动前先跑一遍）

1. 代码层
   - 检查 `force-dynamic` 是否只在必要路由使用。
   - 检查布局是否每次都读取会话（可优化为“公开侧不查会话”）。
   - 检查 Markdown 渲染是否每次都走完整插件链。

2. 查询层
- 检查首页/分类/标签列表是否有重复 `count` + `rows` 两次扫描的 SQL。
- 检查分页是否有 `count(*)` 必要性，能否降频执行。
- 检查是否能把“数量”与“列表”查询拆到不同请求间隔更新。

3. 配置层
- 是否开启 HTTP 缓存头；是否有 CDN 或反向代理缓存层。
- 是否有证书、HTTPS 和重定向链路导致额外请求。
- 是否已有日志采样，避免大量 debug 日志拖慢响应。

## 九、目标能力（给你自己设的验收线）

1. 单机轻量稳定目标
   - 长稳 QPS：60~80。
   - 峰值短时 QPS：90~120，P95 持续低于 400ms。
2. 运维目标
   - 24/7 可读写服务不重启。
   - 数据库锁冲突出现可被监控到并有告警。
3. 用户体验目标
   - 文章列表和详情不因高并发出现明显抖动。
   - 深夜空闲时响应可回到基线状态。

## 十、下个版本直接可执行清单（按优先级）

1. 先把“文章列表 count + 详情”拆缓存，先不碰主题逻辑。
2. 再加查询层索引并移除重复扫描。
3. 最后补充公开页缓存与刷新链路。
4. 每做一项只改一个文件族，改后补 15 分钟压测结果到 `server-capacity.md`。
