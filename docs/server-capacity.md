# 生产服务器容量评估

评估日期：2026-07-26

## 当前部署架构

```text
Internet -> Nginx -> Next.js (next start, port 8000) -> Node SQLite
```

- 单台 CentOS Stream 9 虚拟机
- Nginx 反向代理到单个 Next.js 生产进程
- SQLite 数据库存放在 `/opt/next-typecho/data/`
- 当前没有 CDN、页面缓存层或 Node 多进程

## 服务器规格与基线

| 项目 | 实测值 |
| --- | --- |
| CPU | 2 vCPU，Intel Xeon Platinum |
| 内存 | 1.7 GiB |
| Swap | 未配置 |
| 磁盘 | 40 GiB，总使用率约 48% |
| 空闲负载 | 0.00 / 0.02 / 0.00 |
| Next.js 服务内存 | 压测前约 231 MiB，压测后约 328 MiB |

## 首页读取压测

压测从生产服务器本机发起，路径为 `127.0.0.1 -> Nginx HTTPS -> Next.js`，因此覆盖了 Nginx 与应用层，但不包含用户到公网的网络延迟。

| 并发数 | 请求数 | 成功率 | QPS | P50 | P95 | 最大响应时间 |
| --- | --- | --- | --- | --- | --- | --- |
| 10 | 300 | 100% | 97.8 | 92.4 ms | 170.8 ms | 257.5 ms |
| 20 | 300 | 100% | 117.5 | 172.2 ms | 202.8 ms | 221.7 ms |

压测后服务保持健康，系统可用内存约 808 MiB，未出现请求失败。

## 容量结论

`117.5 QPS` 是短时、预热后的首页读取测试结果，不能作为生产承诺上限。基于当前单进程 Next.js、2 vCPU、1.7 GiB 内存与 SQLite 的组合，采用下列运行目标：

| 场景 | 建议容量 | 说明 |
| --- | --- | --- |
| 动态页面读取 | 60-80 QPS | 长时间稳定运行的保守目标 |
| 短时浏览突发 | 约 100 QPS | 应保持监控，不应作为持续负载 |
| 后台/评论等写入 | 5-10 QPS 以下 | SQLite 同时只能可靠地处理一个写入者，需单独压测确认 |

普通个人博客的读多写少模式下，当前配置可以支撑数百至上千名同时浏览的用户。实际并发用户数取决于用户停留时间、静态资源缓存命中率、文章大小以及是否频繁提交评论或后台保存。

## 风险与限制

- 未配置 Swap。流量尖峰、Node 内存增长或构建误在服务器执行时，可能触发 OOM。
- SQLite 很适合当前读多写少的博客，但评论、点赞、发布等高并发写入会受到单写入锁限制。
- 首页结果不能代表所有页面。复杂 Markdown、图片处理、搜索与写入接口需要分别压测。
- `src/app/api/system-stats/route.ts` 会读取 CPU、内存、磁盘与网络指标，不应作为公开高频接口；应限制为管理员访问并降低轮询频率。

## 扩容与优化阈值

满足任一条件时，应开始优化或升级：

- 动态读取长期超过 60 QPS，或 P95 响应时间持续高于 500 ms。
- 可用内存长期低于 300 MiB，或出现 OOM / 服务重启。
- 评论、后台保存等写入请求出现 SQLite 锁等待或失败。

优先顺序：

1. 静态资源接入 CDN，并为公开读取页增加缓存策略。
2. 对登录、评论、系统状态接口增加限流；系统状态接口只对管理员开放。
3. 升级到至少 `2C4G`，以留出 Node、系统缓存和流量尖峰的内存余量。
4. 当写入成为主要负载时，从 SQLite 迁移到 PostgreSQL 或 MySQL。

## 复测建议

- 每次大版本升级、主题大改或数据库结构调整后复测首页、文章详情、搜索和写入接口。
- 压测时同时记录错误率、P95/P99、服务 RSS、系统可用内存、CPU 与 SQLite 锁错误。
- 线上压测应从低并发开始，避免在真实访问高峰执行。
