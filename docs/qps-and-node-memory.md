# 服务性能调优沉淀：Node 堆内存与 QPS

## 结论先行

1. 提高 Node.js 堆内存可以提升稳定性与抗抖动能力，但并不能线性提升 QPS。
2. 该项目的 QPS 上限通常由多因素共同决定：数据库（SQLite）、缓存命中、Nginx 代理策略、并发 worker 数、日志与磁盘 I/O。
3. 推荐先做“系统性优化”，再考虑大幅提升堆内存。

## 性能瓶颈优先级（从高到低）

1. SQLite 并发与查询模式
   - 写冲突与长事务会拖慢整站。
   - 未命中缓存的动态页和频繁查询会直接放大数据库压力。
2. 缓存策略
   - 静态资源与公共页面若未走缓存，会把 Nginx 与 Next.js 都推高。
3. Node 进程配置
   - 单实例可用并发有限，worker 与堆设置直接影响抖动、GC 和稳定性。
4. Nginx 配置
   - 连接复用、超时、缓冲会影响吞吐与尾延迟。
5. 磁盘与日志
   - 磁盘 I/O 瓶颈会拖慢系统级响应，尤其是请求日志、上传、静态资源。

## 当前建议（按影响大小）

### 1) 先确认部署链是否“干净”
- 证书配置更新、服务启停、环境文件均正常；部署脚本见 [docs/deployment.md](deployment.md)。
- 重点先确认是否是“页面缓存不足/查询重复”，而非纯堆内存问题。

### 2) 调整 Node 堆
- 先从保守值开始：`--max-old-space-size=1536`（或 `2048`）
- 观察 1~2 小时监控曲线，不要直接拉到很高（例如 4096）以免 GC 停顿变重。

推荐环境变量配置（服务层）：

```bash
export NODE_OPTIONS="--max-old-space-size=1536"
```

### 3) 确认并发模型
- 在小内存机器上建议先用单实例 + 合理并发限制。
- 有多核场景可配多个实例（或并发 worker），但要配合数据库和内存预算。

### 4) Nginx 优化方向
- 静态资源长期缓存：`Cache-Control`、`ETag`、`expires`。
- 反代保守开启：`proxy_buffering`、`keepalive`，避免过度占用连接。

### 5) 数据库与 SQL
- 为高频查询补索引，控制分页长度。
- 避免首页和归档页每次请求重复扫描、重复聚合。
- 大量并发写场景考虑降级策略或异步化。

### 6) 监控与回滚
- 重点看 3 个指标：P95/P99 延迟、CPU 利用率、数据库等待时间。
- 调整不当时要按 2~3 个级别回滚：
  - Node 堆从 2048 降到 1536
  - 逐步恢复 worker 并发参数
  - 回退到先前稳定的 Nginx 缓存策略

## 一次可执行的压测思路（便于复盘）

1. 记录基线（修改前）：QPS、P95/P99、CPU、内存、SQLite 读写耗时。
2. 调整一项参数，保持其余不变，观察 15~30 分钟。
3. 只保留改进明显且无异常抖动的参数。
4. 每次改动做小步迭代并在此文档记录参数与结果。

## 结语

可以把“提高堆内存”当作“稳定性兜底”，但 QPS 能否明显上来，通常要靠缓存、数据库、Nginx 三位一体一起优化。只改单项（只加内存）常常“有改善，但不够明显”。
