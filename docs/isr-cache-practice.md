# 首页与文章详情的静态/短时 ISR 落地指南

更新时间：2026-07-26

你关心的“首页和文章详情尽量走静态或短时 ISR”可以按这个理解来做：
- 把每次请求都计算的页面改成“先读缓存，再按周期刷新”。
- 对写操作（发表/编辑）做“立即失效”处理，保证编辑后不久即生效。

## 1. 目标

1. 降低数据库和 Markdown 实时渲染压力
2. 降低 P95/P99 波动，提升并发稳定性
3. 保持写操作（发布、编辑）快速可见

## 2. 适用范围

建议给以下页面先接入：
- 首页（`/`）
- 文章详情页（`/posts/[slug]`）
- 分类/标签列表页（可后续逐步扩展）

不建议强制改造为 ISR 的页面：
- 管理后台
- 登录/会话相关接口
- 写入类接口

## 3. 三种策略（按复杂度）

### 3.1 静态优先 + 短时 revalidate（推荐先上）
- 为首页/详情页增加服务端缓存边界。
- 设置短时更新窗口，比如 30 秒到 300 秒。
- 这样读多的时段可以复用缓存结果，不会每次查库。

### 3.2 事件驱动失效（发布后立即更新）
- 文章发布/编辑后调用缓存失效接口（例如 `revalidatePath` / `revalidateTag`）。
- 避免用户看到过旧内容太久。

### 3.3 进阶：详情页 HTML 预缓存
- 文章保存时生成 `renderedHtml` 并入库存储。
- 详情页优先读缓存 HTML，降掉 Markdown 实时解析成本。
- ISR 负责页面级刷新，内容缓存负责文档级渲染复用。

## 4. 为什么对你当前项目有效

你现在是“读更多、写少”模式，公开页是高频请求入口。
- `force-dynamic` 太宽时，每个请求都会触发查库和渲染。
- 仅靠加服务器内存不一定改善尾延迟。
- ISR 让重复请求直接命中缓存，天然降低抖动。

## 5. 推荐落地步骤（最小改动）

1. 先在公开页加 `revalidate` 控制（先 60 秒起）；
2. 把 `force-dynamic` 从公开页移除（仅保留后台和用户态敏感页）；
3. 加“发布/编辑”时的 revalidate 清理：
   - 清理该文章详情路径
   - 清理首页路径
   - 清理受影响分类/标签列表路径
4. 观察 24 小时监控：
   - P95/P99
   - 每秒请求数
   - 数据库查询耗时
5. 若仍有抖动，再加文章详情内容预缓存（数据库字段缓存 HTML）。

## 6. 示例代码思路（方向）

### 6.1 页面级重验证（概念）
- 页面返回时设置 `revalidate`，表示“短时缓存窗口”。
- 在内容更新后调用 `revalidatePath('/posts/[slug]')`。

### 6.2 文章更新动作后触发
- 在创建/更新 action 中：
  1. 写库（文章正文、摘要、状态）
  2. 触发页面缓存失效
  3. 返回成功

> 注意：`revalidate` 的目标是“读路径稳定”，不是“替代数据库真数据源。

## 7. 参数建议（先用这组）

- 首页：`revalidate = 60`（你可先试 30~120）
- 文章详情：`revalidate = 120`（或按内容更新频率调）
- 侧边栏区块：独立更短 TTL（30~60），减少重复渲染

## 8. 风险与回退

1. 缓存不及时：
- 通过失效链路确保编辑后立即更新。
2. 旧数据展示：
- 首页/详情可接受短暂旧页面，通常在你博客场景可接受。
3. 回退策略：
- 若出现异常，可先降级：把 TTL 拉短或临时移除失效标签逻辑，回到动态页先保稳定。

## 9. 你现在可以直接执行的动作清单

1. 不改功能逻辑先改路由缓存边界；
2. 观察 1 个自然日；
3. 再加文章详情预缓存；
4. 最后补充分类/标签列表页。
