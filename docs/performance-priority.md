# 性能优化优先级沉淀（基于当前博客现状）

更新时间：2026-07-26

## 结论先行

当前最需要先改的是「公开读路径」而不是服务端内存。
收益最高的顺序是：

1. 公开页去动态化（接入短时缓存）
2. 统一减少重复数据库查询
3. Markdown 渲染结果缓存

---

## 1）最优先：公开页动态转缓存（首页/分类/标签/详情）

问题：
- 这类页面高频访问，但每次都重算。
- 即使是“只读”的内容，也让数据库和渲染链路每秒重复工作。

要改的地方：
- 逐步移除不必要的 `force-dynamic`。
- 给首页、分类、文章详情页设置 `revalidate`。
- 保留后台、登录、会话/权限敏感页面为动态。

效果预期：
- 请求中的重复数据库查询和渲染大幅下降。
- P95/P99 明显改善，峰值时波动下降。

---

## 2）第二优先：查询层减负（列表 count + 附属查询）

问题：
- 文章列表常见的 `count + 分页列表 + 额外聚合` 在高并发下重复触发。
- 分类/标签页也会走多次子查询，放大数据库压力。

要改的地方：
- 先识别页面级公共查询（最近文章、归档、标签云、热门文章）。
- 加服务层缓存（内存/文件/Redis）并定义失效时机。
- 逐步消除 N+1 读法，改为批量读取或一次 join。

效果预期：
- SQL 调用次数下降。
- 单次请求 DB 延迟减少。
- SQLite 锁/等待概率下降。

---

## 3）第三优先：Markdown 渲染缓存

问题：
- 长文 + 公式 + 代码高亮 + Mermaid 的组合在详情页开销较高。
- 重复访问同一篇文章会重复消费 CPU。

要改的地方：
- 文章发布/编辑时离线生成渲染 HTML（或结构化缓存）。
- 详情页优先返回缓存 HTML，回退时再实时渲染。
- 内容变更时清理对应缓存。

效果预期：
- 详情页 CPU 峰值下降。
- 读多场景下响应更稳定。

---

## 4）不建议优先改的方向

- 单纯提高 Node 堆（可改善稳态/抗抖，但不是压榨 QPS 的第一手段）。
- 为所有页面“全量缓存”或无条件关闭动态（会影响后台态/权限态正确性）。

---

## 5）执行顺序建议（7 天内可落地）

1. 先接 `revalidate` 到首页和文章详情（最小改动）。
2. 再接入查询缓存（首页侧边栏相关查询）。
3. 再做文章 HTML 缓存（发布/编辑更新时写入）。
4. 每步仅改一层，改完补一组压测指标（QPS/P95/P99/CPU/DB 等）。

---

## 6）验收标准（建议作为你自己的 KPI）

- 长稳 QPS 目标：60~80（当前配置）
- 突发 QPS 阶段 P95 < 400ms
- 文章详情重复访问时，CPU 峰值下降且无明显抖动
- 数据库查询超时/锁冲突明显下降
